# 09 — Configuration & Secrets

**Goal:** One config format (TOML, already chosen — see
`docs/toml-migration.md`), one loader, one schema-validation step,
environment-variable overrides, and a sane secrets story.

## 1. Config files (target layout)

```
conf/
  bnetd.toml          (canonical; was `bnetd.conf`)
  d2cs.toml
  d2dbs.toml
  channel.conf        (data file — list of channels; stays .conf-style)
  bnban.conf          (data file)
  ...                 (other *.conf.in templates are *data*, not config)
```

The distinction matters: **config** describes daemon behaviour
(ports, paths, logging); **data** is content (channel names, banned
IPs, MOTD). Data files don't need TOML.

## 2. Loader

`src/v3/infra/config/` has the loader. Public API:

```cpp
namespace pvpgn::config {

struct BnetdConfig {     // typed, exhaustive
  net::Listener  bnet_listener;
  net::Listener  telnet_listener;
  net::Listener  irc_listener;
  persistence::DbConfig  db;
  logging::LogConfig     log;
  scripting::LuaConfig   lua;
  // …
};

[[nodiscard]] core::Result<BnetdConfig, core::StatusCode>
    load_bnetd(std::filesystem::path file,
               std::span<const char* const> argv);

}  // namespace
```

- Single source of truth: typed struct, designated-initialiser–
  friendly defaults.
- Loader merges in this order: built-in defaults → TOML file → env
  vars (`PVPGN_BNETD__NET__BNET_LISTENER__PORT=6112`) → CLI flags.
- Validation runs after merge. Bad config ⇒
  `StatusCode::ConfigError` with a clean diagnostic
  (`field=net.bnet_listener.port reason="port out of range"`).
- The loader does **not** read the filesystem outside the config
  file path itself; resolved paths inside config are passed to
  consumers verbatim (each consumer adapter validates its own
  paths).

## 3. Schema discovery & docs

- Each `*Config` struct has a `to_schema()` reflection-style helper
  (use macros or a small code-gen step — YAGNI says macros first).
- `pvpgn-config --print-schema` dumps the schema as Markdown.
- `pvpgn-config --validate <file>` runs the loader and exits non-zero
  on error.
- `docs/config-reference.md` is generated by the schema dump in CI;
  drift fails the build.

## 4. Hot reload

- Out of scope by default (YAGNI). Most operators restart on config
  change.
- The internal API is structured so that `services::*::reload()`
  could be added later: load a new `BnetdConfig`, diff against
  current, apply per-subsystem.

## 5. Secrets

What counts as a secret in pvpgn:

- DB passwords.
- s2s shared keys (d2cs ↔ bnetd, d2dbs ↔ d2cs).
- Plugin API tokens, if any.

Handling:

- A secret in TOML is a string value of the form
  `"env:VAR_NAME"` or `"file:/path/to/secret"`. The loader
  resolves these at load time; plain strings are also accepted but
  logged at `warn` (`secret %s is inlined in config — prefer env: or
  file:`).
- Loaded secrets are `core::Secret<std::string>`: a wrapper that
  zeroises on destruction and refuses to format itself (its
  formatter prints `"***"`).
- `core::Secret` lives in `core/secret.h`. No secret value ever
  reaches the logger directly.
- File-backed secrets: refuse to read if file is world-readable on
  POSIX (`stat` mode 0644 → error). Configurable override for
  weird mounts.

## 6. Per-environment overlays

Optional include directive in TOML (`include = "conf.d/*.toml"`).
Each included file overlays on the merged config in lexical order.
Useful for ops to keep `00-base.toml` + `10-prod.toml` separate.
