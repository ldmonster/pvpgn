# 13 · Web UI (Admin REST/WebSocket + SPA)

PvPGN today has no web management surface — administrators rely on the
telnet console (`handle_telnet`), the Win32 GUI (`win32/console_*`),
and direct edits of `bnetd.conf`. The refactor adds a first-class web
control plane.

## 1. Goals

* Real-time **operations dashboard**: online users, active games,
  channels, throughput, errors.
* **Account administration**: list/search, ban/unban, kick, reset
  password, set command groups, edit attributes safely.
* **Channel & game moderation**: list, inspect members, kick/silence,
  topic edit, close.
* **Ladder & tournament management**: view leaderboards, schedule
  tournaments, brackets, broadcast announcements.
* **Configuration UI**: edit `bnetd.toml` keys with validation;
  hot-reload via `SIGHUP` saga.
* **Plug-in/scripting management**: install, reload, enable/disable,
  inspect logs.
* **Audit log viewer**.
* **Public read-only pages** (optional, configurable): top players,
  current channel population, server status banner — for community
  websites.
* **API for third parties**: stable REST/OpenAPI 3.1 + WebSocket
  subscriptions; eventual gRPC.

## 2. Stack

### 2.1 Backend (in-process, C++)

* **Boost.Beast** (HTTP/1.1 + WebSocket) on top of the same
  `IoRuntime`; one fiber per request — async parsing & dispatch.
* **Routing**: a tiny `Router` (path → handler) built in-house; we do
  NOT introduce a heavy framework like Crow because Beast + fibers
  already gives us what we need.
* **Auth**: JWT (HS256 by default, RS256 optional). Tokens issued via
  `POST /api/v1/auth/login` with PvPGN account credentials, or via
  an OIDC bridge (configurable, optional).
* **RBAC**: same `CommandGroup` model as in-game; admin web UI requires
  `admin` group; moderators get a reduced surface.
* **Rate limiting**: per-IP and per-token leaky bucket.
* **CSRF**: not applicable to a token-based API. Cookies optional and
  same-site.
* **CORS**: configurable; defaults to same-origin.
* **TLS termination**: built-in (OpenSSL), or reverse-proxy via nginx
  (the recommended prod mode).
* **OpenAPI**: hand-curated `openapi.yaml` checked into the repo;
  responses generated by typed handlers.

### 2.2 Frontend SPA

* **TypeScript + React 18 + Vite + TanStack Query + Zustand**.
* **UI**: shadcn/ui (Radix + Tailwind) — accessible, themeable, low
  dependency cost.
* **Charts**: Recharts.
* **i18n**: react-intl.
* **Auth**: stores JWT in memory (refresh token in HttpOnly cookie
  optional).
* **Live updates**: a single WebSocket subscription with topic
  multiplexing (`channels`, `games`, `users`, `events`).
* **Build output**: static assets bundled into the C++ binary via
  CMake's `configure_file` + a small `EmbeddedAssets` table (zlib
  compressed) — single binary deploys, no separate web server
  required. (Operators may still front with nginx if they prefer.)

## 4. WebSocket channels

```
ws://host/api/v1/ws

  → subscribe { "topic": "events" }              # all domain events
  → subscribe { "topic": "channel:0xABCD" }      # one channel's chat
  → subscribe { "topic": "game:1234" }
  → subscribe { "topic": "console" }             # live command echo

Server → { "topic": "...", "event": {...} }      # JSON-encoded events
```

The hub fans events from `IEventBus` to subscribed sockets via
`boost::fibers::buffered_channel`. Backpressure: slow consumers are
dropped with a `slow_client` event after a threshold.

## 5. Auth & permissions

* The web UI uses the **same** `Account` aggregate. There is no
  separate "admin" user table.
* Web login requires `command_groups & admin_web != 0`. The default
  config maps the existing `admin` group to `admin_web`.
* Optional `2FA TOTP` via a small `domain::identity::Totp` value
  object stored alongside the password hash.
* Tokens carry the `AccountId`, `groups`, `iat`, `exp`. Validation in
  `infrastructure/webapi/jwt.cpp`. No DB hit on each request.

## 6. Operational features in the UI

* **Live console** (`/console`) emulates the telnet operator session
  by piping `ICommandBus` over WebSocket — replaces the `bnbot` tool
  and the telnet port can be disabled.
* **Hot config editor** with diff preview and rollback (last 10
  versions kept in `/var/lib/pvpgn/config-history/`).
* **Migration runner** UI: show pending DB migrations, apply, rollback
  manually if needed.
* **Plugin manager**: upload `.zip`, view manifest, capabilities,
  enable/disable, see per-plugin logs.

## 7. Security hardening

* HSTS, CSP `default-src 'self'`, frame-ancestors deny, X-Content-Type
  nosniff, Referrer-Policy strict-origin.
* Argon2id for **web-only** auxiliary password verification (optional;
  default keeps the BNet-compatible SHA-1 hash so a single password
  works for in-game and web).
* `httpOnly` refresh cookie, `Secure` when TLS.
* Per-route audit log entries via `application/admin/audit.cpp`.
* CI: zap baseline scan, npm audit, `gosec`-equivalent for the C++
  side (`semgrep` ruleset).

## 8. Why "in-process" instead of a sidecar

* Direct in-memory access to `IEventBus` and repositories — no extra
  serialisation hop for live metrics or chat tail.
* Single deployable; matches the "single binary" ethos of PvPGN.
* Beast/asio fits naturally on the existing `IoRuntime` fiber pool;
  the WebUI handlers literally compete with game-protocol fibers on
  the same scheduler, sharing one event loop.
* Operators who prefer isolation can disable the embedded server and
  let an external service consume the same gRPC/REST surface (a
  stretch goal for 3.x).

## 9. Public, optional widgets

A read-only sub-route (`/public/...`) can be enabled in config for
community sites:

* `GET /public/v1/status` → `{ online, users, games, version }`
* `GET /public/v1/ladder/{tag}/top?n=50`
* `GET /public/v1/channels?tag=STAR` (counts only)

Behind aggressive caching headers; no auth.

## 10. Testing the WebUI

* Backend: integration tests under `tests/integration/webapi/` spin a
  fake `IoRuntime` and a fake auth provider.
* Frontend: Vitest for components, Playwright for happy-path E2E
  (`tests/e2e/webui/`).
* Contract tests assert that the typed TS client matches `openapi.yaml`
  (`openapi-typescript --check`).
